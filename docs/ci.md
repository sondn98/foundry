# Image CI/CD

How container images in this repository get validated and published.

## Repository layout

Every image lives in its own top-level folder:

```
<app>/
  Dockerfile     # required — the image definition
  VERSION        # required — one line, semver, e.g. 2.336.0
  CHANGES.md     # human-written changelog
  ci.yaml        # optional — per-app build configuration (see below)
```

**Discovery is dynamic.** Any top-level folder tracked by git that contains both a `Dockerfile` and
a `VERSION` is an application. There is no list of app names anywhere in the workflows — adding a
folder is all it takes to onboard an image.

> One gotcha: `.gitignore` is the stock Python template, so it ignores directories named `lib/`,
> `build/`, `dist/`, `var/` and `share/`. A folder with one of those names would be invisible to git
> and therefore to discovery. Pick a different name.

## Adding a new image

1. Create `<app>/` with a `Dockerfile`, a `VERSION` (e.g. `0.1.0`) and a `CHANGES.md`.
2. Optionally add `<app>/ci.yaml` if the defaults don't fit.
3. Open a PR against `master`. The pipeline picks it up automatically.

That's it. No workflow edits.

## What runs when

| Trigger | What happens | Publishes? |
| --- | --- | --- |
| PR → `master` | Validate versions/changelogs, secret scan, Dockerfile lint, build **all** target platforms, vulnerability scan | **Never** |
| Push → `master` (merge) | Build and push to Docker Hub — but only for folders whose `VERSION` changed in that push | Yes |
| `workflow_dispatch` | Manual escape hatch: pick an app (or all), publishing is an opt-in checkbox | Only if you tick `publish` |

Nothing outside these three triggers touches the registry.

### Pull request checks

For every application folder the PR touches:

- **Semver validity** — `VERSION` must be exactly one line of well-formed semver
  (`MAJOR.MINOR.PATCH`, optional `-prerelease` / `+build`, no leading `v`).
- **Version increase** — if `VERSION` changed it must be strictly greater than the value on
  `master`, using semver precedence (`3.2.3-rc1` < `3.2.3`). A brand-new folder has no baseline and
  is exempt.
- **Changelog rule** — if `VERSION` changed, that folder's `CHANGES.md` must have changed in the same
  PR. Editing `CHANGES.md` *without* a version bump is fine. The content of the entry is not checked.
- **Dockerfile lint** — hadolint, failing on `error` severity. Warnings appear as annotations.
- **Dockerfile misconfiguration** — Trivy config scan, informational only.
- **Vulnerability gate** — Trivy scans the freshly built image and fails on `CRITICAL` findings that
  have a fix available (`--ignore-unfixed`). `HIGH` findings are reported in the job summary but do
  not block.
- **Secret scan** — gitleaks over the repository.
- **Build** — the image is built for every target platform to prove it still builds. Nothing is
  pushed.

Results land in a sticky PR comment with a per-app pass/fail table, so you don't have to open logs.

### Publishing

A push to `master` publishes a folder **only if that push changed the folder's `VERSION`**. Changing
just the Dockerfile without bumping `VERSION` is a deliberate no-op — bump the version to ship.

Images are published to `docker.io/sondn98/<folder>`.

Tags pushed:

| Tag | When |
| --- | --- |
| `<version>` | always |
| `sha-<short>` | always — traces an image back to a commit |
| `latest` | stable releases only, **never** for a pre-release like `3.2.3-rc1` |

If a tag already exists in the registry it is **overwritten**. There is no immutability check.

Each published image also carries an SBOM and SLSA provenance attestation (generated by buildx), plus
OCI labels for title, version, source and revision.

## Per-app configuration: `ci.yaml`

Optional. Without it an app builds for `linux/amd64,linux/arm64`, is named after its folder, and
passes no build args — the Dockerfile's own `ARG` defaults stay authoritative.

The parser accepts a deliberately small, flat subset of YAML (no external tooling is available on the
self-hosted runners, so it is hand-parsed and strictly validated):

```yaml
# <app>/ci.yaml — every key is optional

# Repository name under docker.io/sondn98/. Defaults to the folder name.
# Include a '/' to override the namespace entirely.
image: arc-runner

# Comma-separated, ON ONE LINE. A YAML block list is rejected.
platforms: linux/arm64

# Passed to the build as --build-arg. Omit to keep the Dockerfile's defaults.
build_args:
  - RUNNER_VERSION=2.336.0
  - HELM_VERSION=v3.21.3
```

Rules the parser enforces, loudly:

- Comments must be on their own line — no trailing `# ...` after a value.
- `platforms` must be a single comma-separated string, not a block list.
- `build_args` entries must be `KEY=value` and may not contain quotes or backslashes.
- Unknown top-level keys are an error, so a typo can never silently change what gets built.

## Runners

Jobs run on `${{ vars.CI_RUNNER_LABEL }}`, falling back to `ubuntu-24.04` when that repository
variable is not set. Set it to your ARC scale set name to run on self-hosted runners.

Two things to know if you point this at the ARC scale set:

- **Docker is required.** Every job builds images and several actions (hadolint, Trivy, gitleaks) are
  container actions. The scale set must run in Docker-in-Docker or Kubernetes mode with a working
  Docker socket. The stock `ghcr.io/actions/actions-runner` image has no Docker CLI.
- **Bootstrap.** `arc-runner` is the image that *feeds* that scale set. If the scale set is broken,
  the job that would fix it cannot run. Keep `ubuntu-24.04` (unset the variable, or use
  `workflow_dispatch`) as the recovery path for that one image.

Cross-architecture stages are emulated with QEMU, which is slow — an arm64 build on an amd64 runner,
or vice versa, can take several times longer than a native one.

## Caching

Layers are cached with GitHub Actions cache (`type=gha`), scoped per app, and shared between the
scan build and the multi-platform build in the same run.

## Secrets and variables

| Name | Kind | Purpose |
| --- | --- | --- |
| `DOCKERHUB_USERNAME` | secret | Docker Hub account name |
| `DOCKERHUB_TOKEN` | secret | Docker Hub **access token** (not your password), Read/Write scope |
| `CI_RUNNER_LABEL` | variable | Optional. Runner label; defaults to `ubuntu-24.04` |

Secrets are referenced by name only and reach the reusable workflow via `secrets: inherit`. They are
used solely on the publish path — a pull request never logs in to the registry.

## Files

| File | Role |
| --- | --- |
| `.github/workflows/ci.yml` | Triggers, discovery, PR gates, matrix fan-out, PR report |
| `.github/workflows/build-image.yml` | Reusable workflow: lint → scan → build → publish, for one app |
| `.github/scripts/appconfig.sh` | App discovery, `VERSION` reading, `ci.yaml` parsing |
| `.github/scripts/semver.sh` | Dependency-free semver validation and comparison |
| `.github/scripts/discover.sh` | Builds the JSON matrix of apps to act on |
| `.github/scripts/validate.sh` | PR governance checks |
| `.github/dependabot.yml` | Keeps the SHA-pinned actions current |

## Conventions

- Third-party actions are pinned to full commit SHAs with a `# vX.Y.Z` comment; Dependabot updates
  both.
- `permissions:` is `contents: read` by default; only the report job gets `pull-requests: write`.
- Concurrency: one run per PR (superseded runs cancelled), and one build at a time per app per ref so
  two merges cannot race to the same tag.
